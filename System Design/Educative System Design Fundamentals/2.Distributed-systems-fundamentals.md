# Time in distributed systems

When a server runs on a single server, it is easy to tell the order of events as the server's clock give a clear timeline.

However, when an application runs on multiple servers that are in different locations, this becomes challenging.

**For example:** Imagine two friends sending messages to eachother at the same time in a chat app running on different servers, the system must determine the order to display these messages. And because each server has its own clock that might not be perfectly synchronized, relying on timestamps alone can cause confusion about which message came first. Instead, the system uses logical time or other ordering methods to ensure messages appear in a consistent and sensible sequence, even if the exact sending times are unclear.

Imagine below:

```
[Alice's Phone]                         [Charlie's Phone]
   (New York)                                (Tokyo)
       |                                        |
  (Cell Tower)                             (Cell Tower)
       |                                        |
[Server A (New York)]====================[Server B (Tokyo)]
       |              (Undersea Cables)         |
       +-----------------[Database]-------------+
                             |
                       [Bob's Phone]
                          (London)
```

Imagine Alice (in New York) and Charlie (in Tokyo) both send a message to Bob at the exact same moment.

- Alice’s message goes to the New York Server.
- Charlie’s message goes to the Tokyo Server.
- Both servers need to forward their messages to Bob.

Bob's phone needs to know which message to display first on his screen. The intuitive solution is to use the timestamps from the servers: whichever message has the earlier time goes first.

However, physical time introduces two major issues:

1. **Clock Drift:** every server has its own internal physical clock. No matter how tightly they are synchronized, the clock in Tokyo might be 50ms faster than the clock in New York. If Alice and Charlie press send at the exact same true moment, the Tokyo server will stamp Charlie's message with a slightly later time simply because its clock is running fast.
2. **Network Latency:** The physical distance between New York, Tokyo, and London means data takes time to travel. Alice's message might get delayed by 150 milliseconds due to a minor network hiccup across the Atlantic ocean, causing it to arrive at Bob's phone after Charlie's.

If the system relies on physical time (wall-clock time), Bob might see Charlie's message above Alice's, even if Alice actually sent hers a fraction of a second earlier. In a fast-paced group chat, messages can appear completely out of conversational order.

More sequential and ordered example:

What reaches Bob's phone is a data packet containing the message text, the sender's identity, and the server's timestamp (the physical stamp). The chat app on Bob's phone stores these arriving messages in a local database and continuously sorts them on the screen by looking at those timestamps, ordering them from oldest (top) to newest (bottom).

Here is exactly what happens step-by-step on Bob's phone that causes the order to break in the physical time scenario:

- **The First Arrival:** At true time 10:00:00.060, Charlie's message arrives first because it had less network delay. It carries the physical timestamp 10:00:00.060 (due to the Tokyo server's fast clock). Bob's app displays it. For a fraction of a second, Bob only sees Charlie's message.

- **The Second Arrival:** At true time 10:00:00.160 (100 milliseconds later), Alice's message finally makes it through the long Atlantic network delay. It arrives carrying the physical timestamp 10:00:00.010 (from the accurate New York server).

- **The Re-Sort:** Bob's app receives this new message and must update the screen. It looks at the timestamps to figure out where to place it in the chat history. It compares Alice's stamp (.010) against Charlie's stamp (.060).

- **The Glitch:** Because .010 is mathematically smaller (older) than .060, the app's logic determines that Alice must have spoken first. The app forcefully inserts Alice's message above Charlie's on the screen.

From Bob's perspective, the UI suddenly jumps. Charlie's message gets pushed down, and Alice's message magically appears above it, abruptly rewriting the conversational history right before his eyes. This is why relying on physical time fails: the app is forced to trust faulty server clocks over the actual order in which the data arrives.

Network delays and inaccurate clocks can cause errors, such as messages appearing in the wrong order or even data being lost. Ensuring events are ordered correctly is one of the primary challenges in distributed System Design. **To solve this, we do not depend only on physical time. Instead, we use logical time, which tracks the order of events across the system rather than relying on wall-clock time.**

## Why is time challenging in distributed systems ?

In DS there is no single source of truth for time. This discrepancy creates several fundamental challenges like below:

- **Network latency:** The time it takes for a message to travel from one node to other is variable and unpredictable. A message sent at 10 o clock might reach its destination half a second later or more depending on network conditions.
- **Clock Drift:** Physical clocks on different machines run at slightly different rates. Over time, even clocks that were once synchornized will drift apart.
- **Unreliable synchronization:** Clock synchronization mechanisms can fail or introduce their own delays, making it unsafe to assume that all nodes share the same view of time. 

These challenges directly impact a system’s ability to maintain consistency, coordinate actions between nodes, and debug problems.

To overcome these physical limitations, engineers developed logical clocks, which focus on the order in which events happen relative to each other, rather than depending on each node’s local clock to timestamp events.

## Logical clocks and event ordering

Because local clocks cannot be fully trusted to order events accurately in a distributed system, we need an alternative mechanism.

Logical clocks offer a way to reason about event ordering without relying on a shared, synchronized physical clock. A logical clock assigns a timestamp—a simple numerical value—to each event. This number does not represent real-world time; instead, it captures the logical sequence of events, indicating which events happened before or after others in the system.

For example, if event a occurs first, it might receive the timestamp 1, event b might receive 2, and so on.

By comparing these logical timestamps, a distributed system can establish a consistent global ordering of events, even when those events occur on different machines with unsynchronized clocks. Logical clocks provide a foundational tool for reasoning about causality and are implemented in algorithms such as Lamport clocks, which we will explore in the next section.

## The Lamport clock algorithm

- A Lamport Clock is not a physical clock that measures time in seconds. It is a logical clock—a simple integer counter maintained individually by each machine (node) in the system to track the sequence of events.
- This is a concrete algorithm for implementing logical clocks.
- Lamport clocks reply on simple software counter inside every server to establish order of events without depending on real world clock
- Instead of using physical timestamps like 10:00:00, we use integer counters that starts with 0 at every server

To keep all the servers in sync, this algorithm uses 3 rules:

1. **Rule 1: The local tick**

Before a server does anything, it will increment its counter by 1

**Example:**
If server A's counter is currently 0 and a user clicks save, server A increases its counter to 1 and then performs the save

2. **Rule 2: The piggyback (sending messages)**

When a server sends a message to other server, it must attach its current counter value to that message.

**Example:**
If server A wants to send a message to server B, Server A's counter is currently at 5, it sends the message with a sticky note saying `[Time: 5]`

3. **Rule 3: The catch-up (receiving messages)**

- This is the most important rule.
- When a server receives a message, it looks at the timestamp on the message and compares it with its own counter.
- It takes which ever number is larger and then adds 1

### Setp-by-step rules

Every node in the system follows these four rules to ensure events can be ordered:

1. **Initialization:** Every node starts with initial counter value `0`
2. **Local Events:** Before a node perfoms any local action, like writing a file or saving data, it increments the counter value by 1
3. **Sending a message:** When sending a message to another node, it attaches its current counter value to that message
4. **Receiving a message:** When a node receives a message, it looks at the counter attached to it and also its local counter, and it increments its local counter to a number greater than both local existing counter value and the receiving value.
5. The formula is: `New_Counter = MAX(Local_Counter, Received_Counter) + 1`

### A Plain English Example

Imagine three servers: Node A, Node B, and Node C. All start with their clocks at 0.

1. Step 1: Node A performs a local task. It increments its clock. (Node A's clock = 1).

2. Step 2: Node A sends a message to Node B. It attaches its clock value (1) to the message.

3. Step 3: Meanwhile, Node B performs a local task. It increments its clock. (Node B's clock = 1).

4. Step 4: Node B receives the message from Node A (which contains the value 1). Node B must update its clock using the formula: MAX(Node B's current clock, Received clock) + 1. This means MAX(1, 1) + 1 = 2. Node B updates its clock to 2 and processes the message.

5. Step 5: Node B sends a message to Node C, attaching its new clock value (2).

6. Step 6: Node C (currently at 0) receives the message. It updates its clock: MAX(0, 2) + 1 = 3.

### The "Happens-Before" Relationship
For interviews, you must understand the happens-before concept (often written as a -> b).

- If event X happens before event Y (meaning X caused Y, or they happened sequentially on the same node), then the Lamport clock of X will always be less than the Lamport clock of Y.

- The Interview Trap: If `Clock(X) < Clock(Y)`, it does not necessarily mean X happened before Y. They could be completely independent, concurrent events happening on different servers at the exact same time. Lamport clocks can tell you if events are ordered, but they cannot definitively identify if events are concurrent.

**Extended explaination for better understanding**

In a distributed systems, we want to know if Event A caused Event B (written as A -> B).
- **What lamport's clock does:** If A -> B, then the clock value of A will always be less than B (L(A) < L(B))
- **The drawback:** The reverse is not true. I mean, If event A timestamp is less than event B, it does not mean that event A must have caused by event B. However, just because \(L(A) < L(B)\), it does not guarantee that event A actually caused or influenced event B (called a lack of causal consistency). The events could be completely independent (concurrent), but Lamport's algorithm will still force a sequential order on them.

**A Simple Example**

Imagine two people on opposite sides of the world who don't know each other:
- Alice in New York buys a coffee at 12:00 PM (Timestamp: 1)
- Bob in Tokyo buys a book at 12:01 PM (Timestamp: 2)

Bob's timestamp (2) is higher than Alice's (1). But Alice buying coffee did not cause Bob to buy a book. They are completely unrelated.Because Lamport's algorithm only looks at the numbers, it mistakenly makes it look like Alice caused Bob's action, when in reality, they just happened around the same time. You cannot trust the numbers alone to tell you the real story.

## The vector clock algorithm

It was created to solve the exact blind spot of lamport clock: distinguishing events between the one that caused another versus events that just happened at the same time independently (concurrently).

Unlike lamport clock, the vector clock algorithm enables system to determine not only the order of events but:
- also whether event A caused event B
- or the events A and B are occured concurrently

To achieve this, instead of single logical clock like the lamport, each node/process maintain a vector clock (array of integers), with a size equal to the total number of process/nodes in a system.

### Working

1. Assume there are three servers - Server 0, Server 1, Server 2
2. Each server maintains self and other servers timestamps in an array. Example: [server 0's time, server 1's time, server 2's time]
3. Servers uses that array to track its own events and uses other slots to remember the latest updates it has heard about the other servers

### 4 rules of vector clock algorithm

1. **The starting line:** When a system boots up, every server starts with a list of zeros [0,0,0]
2. **The local event:** When a server does some action in local, it adds 1 to only its own slot in the array [1,0,0]
3. **Sending a message:** When a server sends a message to other server, it attaches its entire current array to the message
4. **Receiving a message:** When a server receives a message from other server, it does two step process to update list:
    - It goes slot by slot, keeps the highest number between its own list where it belongs or which server it belongs
    - It adds +1 to its own slot because receiving is a local event

**Example:**

1. Assume We have 3 servers so 3 slots [0,0,0]
2. Assume server 1 sends a message to server 2 with [1,0,0]
3. Now server 2 does this, [Max(0,1), Max(0,0), Max(0,0)] = [1,0,0]
4. Next, server 2 adds +1 to its own slot as receiving is its local operation, so, [1,1,0]

**NOTE: Sending or receiving the data add's 1 to the counter for both sender and receiver**

### Lets see how this algorithm solves the draw back of lamport's alogorithm

#### Senario A - Casuality (Happened before)
1. Imagine server 0 has list [0,0] and server 1 has list [0,0]
2. Now server 0 does some local action and list becomes [1,0]
3. And server 1 does some local action and list becomes [1,2]
4. Now, think, how did the server 1 know that server 0 did 1 action in itself ?
5. The only possible way is that server 0 must have sent it a message after doing that action.
6. Which is why, the server 0's slot is exact same in both servers and additional actions happened in server 1 (the 2 in [1,2]) it is the proof that some event happened in server 1 after an event happend in server 0 and that information successfully travelled from server 0 to server 1
7. Extended explanation - look at "Extended explanation of casuality section" below

#### Senario B - Concurrency (Independent events)
1. Imagine server 0 processes an event and gets [1,0]
2. And server 1 processes an event at the same time and gets [0,1]
3. If the system now compares these two lists, it sees a conflict
4. When ever there is a mix of greater thans and less thans across the slots, the algorithm declares the events as concurrent. They happened independently.
5. For example: When system compare point 1 and 2, in slot 0, server 0 is > server 1 and in slot 1, server 1 > server 0. The algorithm declares the events as concurrent

#### Extended explanation of casuality section
You have asked a brilliant question. This exact scenario highlights the superpower of Vector Clocks and why they are used instead of Lamport Clocks.

Your intuition is entirely correct: Server 0 did **not** cause those first 5 actions on Server 1.

The trick to understanding this is that Vector Clocks do not compare the servers as a whole; they compare **specific, individual events**. Let's walk through your exact scenario step-by-step to see how the math perfectly catches this.

**Tracing Your Scenario**

**1. Server 1's Local Actions**
Server 1 does 5 local actions independently. For its 5th action (let's call this **Event X**), its clock is `[0, 5]`.

* *Meaning:* "I have done 5 things. I know about 0 things from Server 0."

**2. Server 0's Send Action**
Meanwhile, Server 0 decides to send a message. It updates its clock to `[1, 0]` before sending. Let's call this **Event Y**.

* *Meaning:* "I have done 1 thing. I know about 0 things from Server 1."

**The Concurrency Test (The Proof)**

Now, let's ask the algorithm: Did Server 0's Event Y `[1, 0]` cause Server 1's Event X `[0, 5]`?

We compare them slot by slot:

* **Slot 0:** `1 is greater than 0` (Server 0 is ahead here).
* **Slot 1:** `0 is less than 5` (Server 1 is ahead here).

Because we have a mix of "greater than" and "less than," the math definitively declares these two events as **CONCURRENT**.

The algorithm successfully proves exactly what you pointed out: Server 0's action did not cause Server 1's first 5 actions. They happened completely independently.

**The Receive Event**

Now, let's look at what happens when the message finally lands at Server 1. Receiving the message is a brand new action (let's call it **Event Z**).

1. **Merge:** Server 1 takes its current knowledge `[0, 5]` and merges it with the incoming message `[1, 0]`. It takes the highest numbers: `[1, 5]`.
2. **Tick:** Server 1 adds 1 to its own slot because receiving is an event.

The clock for **Event Z** is officially `[1, 6]`.

* *Meaning:* "I have now done 6 things total. I also now know that Server 0 did 1 thing."

**The Final Comparison**

If we compare the sending of the message (**Event Y:** `[1, 0]`) to the receiving of the message (**Event Z:** `[1, 6]`):

* **Slot 0:** `1 is equal to 1`.
* **Slot 1:** `0 is less than 6`.

The math says Event Y happened before Event Z. And this is 100% true! The act of *sending* the message definitely happened before the act of *receiving* it.

The Vector Clock acts as a perfect historian. It knows that Server 0 caused the 6th event on Server 1 (the receipt of the message), but it mathematically proves that Server 0 had absolutely nothing to do with the first 5 events.

### Drawback

Vector Clocks give us perfect causality tracking, but their size grows linearly with the number of servers ($O(N)$). In large-scale systems with thousands of nodes, attaching and storing giant vector lists creates massive network and storage overhead. To fix this, systems in practice have to use garbage collection or vector truncating (cutting off old entries) to keep the list size manageable.

## Chandy lamport algorithm

It solves a simple yet critical algorithm - How do you take a snapshot of a global distributed system without stopping its work ?

### The problem - why its needed ?

Imagine a bank has multiple servers and people are using it 24/7 doing money transfer transactions and more. Now you want to gather some data like you want to know if the total amount of money accross all servers is 100$. You know you cannot freeze or stop them servers as it would affect users. So the operations must keep running.

### The inflight trap

#### Scenario

1. Assume you have 50$ in server 1
2. You count it from server A and right after that count, server A sends 20$ to server B
3. Now, server A has 30$ and 20$ are in flight and not yet reached the server B
4. So now you count the server B as 50$
5. The total recorded = 50$ from server A + 50$ from server B = 100$
6. This is correct
7. Assume you counted the balance at server A after it is sent, which will be 30$
8. Now assume server B has received that 20$ and you counted after its received, the balance will be 70$
9. The total recorded = 30$ from server A + 70$ from server B = 100$
10. This is also correct
11. Now, what if that 20$ is in flight and at that time you count the balance in both the servers ?
12. Server A will have 30$ and server B will have 50$ = 80$, 20$ difference and its vanished from the audit

### Core problem

A valid global snapshot should capture 2 things:
1. The local state of each node/process
2. The channel state (all messages/money currently travelling through the network cable)

### Solution - chandy-lamport algorithm

It is a protocol used in distributed systems to record a consistent global snapshot of system without stopping its normal execution. This algorithm uses a special control message called marker that travels alongside regular messages

### Example

Assume Server A and Server B, both has 50$ balance each. Both are connected by a channel (channel A -> B)

1. Server A records its local state: `local state = 50$`
2. Then server A sends 20$ transfer message to server B
3. Then server A immediatly sends a marker right behind the above message
4. Server B receives the transfer message first and it updates its local state with +20$ and becomes 70$
5. Then server B receives the marker
6. Since its the first time it sees the marker, it records its current local state `local state = 70$`
7. It marks channel A -> B as having 0 in-flight messages
8. Final snapshot = Server A has 50$ and Server B has 70$ (its because the server A took snapshot before it sent the transfer message and Server B took it after the transfer message is received)


# Event ordering and consistency models

## Event Ordering

Event ordering models define the rules a distributed system uses to sequence operations across multiple nodes.

### 1. Total Ordering

In total ordering, every node in the system executes event in exact same global sequence. If Node A processes Event 1 before Event 2, Node B must do the same. In simple, in total ordering, all replicas must agree on same order/sequence.

**Example:**
1. Alice deposits 100$ (Event 1)
2. Alice withdraws 80$ (Event 2)
3. If Replicas A and B apply these in different orders, Replica B will reject Event 2 due to insufficient funds
4. Both replicas must agree on total order

### 2. Partial Ordering

The system orders events that are directly related or have a shared key and leaves rest of the events unordered.

**Example:**
On an online shopping site, when you place an order, the system ensures your payment is processed before confirming the order. However, orders from different customers are handled independently, so their confirmations don’t need to follow any specific order relative to each other.

This selective sequencing of events is exactly what partial ordering is.

### 3. Casual Ordering

This is a specialized form of partial ordering that guarantees cause-and-effect relationships are strictly preserved. In other words, if event A causes event B or happened before event B, then every node in the system must observe event A before it observes event B

**Example:**
A group chat thread. If Alice asks "Where should we get lunch?" (Event A) and Bob replies "Let's get pizza" (Event B), everyone must see Bob's reply after Alice's question. However, if Charlie concurrently posts a picture of his cat (Event C), Charlie's photo can appear before or after Alice's question without breaking the conversation's meaning.

## Consistency Models

Consistency models are the rules that a distributed databases use to keep data synchronized across multiple copies when reading and writing.

### 1. Strong Consistency (Linearizability)

A strong consistency is a strict consistency model. It guarantees that all database operations appear to execute in a single, globally agreed order so every read reflects the latest write. In other words, once a write completes, all subsequent reads from any replica reflect that write.

**Example:** In an online banking system, Alice transfers $100 to Bob.

Strong consistency ensures that immediately after the transfer, any balance check by Alice, Bob, or the bank system reflects the updated amounts. Without strong consistency, some replicas might still show the old balances, potentially allowing overdrafts or incorrect transaction histories.

### 2. Casual Consistency

This model is used to maintain a cause-and-effect relationships. meaning, if one operation is dependent on other earlier operation, then all replicas must have seen that earlier operation before the dependent operation.

**Example:** Suppose Alice updates her email address in an app. This update is a write operation to the data store. Right after that, she tries to log in using the new email, which triggers a read operation that depends on the earlier write.
With causal consistency, the system guarantees that the replica serving Alice’s login request has already applied the email update. As a result, Alice can always view her updated email and log in successfully, as illustrated in the slides below. Without causal consistency, her request may be served by a replica that has not yet applied the update, causing the login to fail.

### 3. Eventual Consistency

This is the weakest guarantee model. Eventual consistency means that if a piece of data stops being updated, all copies of that data in the system will gradually become the same. However, it doesn’t ensure that when you read the data, you’ll see the most recent change right away, so temporary differences between copies can occur.

**Example:** In a social media platform, Alice updates her profile picture. Immediately after, some of her friends may still see the old picture due to replication delays. Over time, all replicas synchronize, and everyone consistently sees the updated picture.
